All five current Special rows and all five current Anomaly rows have `CoverStageLv=8` and `AutoChargeId=20001`. Special rows also have `CharacterLv=200`; Anomaly rows have `LimitCharacterLv=400`. The installed `AutoChargeRecord` has `Id`, `Item_type`, `Item_id`, `Auto_charge_plus`, and `Auto_charge_max`; `NK.StaticData.DataManager` exposes `AutoChargeTable`. I did not identify an installed-client battle consumer of the Intercept row's `AutoChargeId`, nor a timing interval for this identifier; the source does not justify applying it to weapon charge or battle energy.

## Original entry and cover computation

The original scene entry path is `ViewInterceptAnomalous.EnterSpotScene` → its async `MoveNext` RVA `0x05BB10A0` → `EnterSpotFromAnomalousInterceptUnit` constructor RVA `0x06D5A3A0`; the Special equivalent is `ViewInterceptSpecial.OnClickEnterInternal` async `MoveNext` RVA `0x05BEAD00` → `EnterSpotFromSpecialInterceptUnit` constructor RVA `0x06D993F0`. Both constructors form an `NKSpotDataTransporter` from the selected static row and wave: they set the wave ID, monster/dynamic object levels, raid level-change group, and battle time. Their callsites do **not** read `CoverStageLv` or `AutoChargeId`. The metadata layout of `NK.Spot.Data.NKSpotDataTransporter` likewise has no field or setter for either name. Shared native RVAs have multiple unrelated managed aliases in the decompiler; identify the call by its receiver and stack destination, not the pseudocode's arbitrary alias label.

The Special constructor passes the static row's `CharacterLv` to `ExtensionSquadDTO.GetCorrectionSquad(Squad,int)` RVA `0x06E011E0`. Its per-character lambda RVA `0x06E119E0` rebuilds a `CharacterSnapshot` using that level. The Anomaly constructor passes `LimitCharacterLv` and two boolean options to the four-argument correction overload RVA `0x06E01060` and lambda RVA `0x06E11BD0`. This account-snapshot correction is broader than simply assigning a level; the diagnostic fixture does not claim to reproduce all of it.

For the **original native cover entity**, `SpotCharacter::.ctor` RVA `0x06384EF0` first copies `SpotCharacterData.Level` (offset `+0x38`) to the character level (`+0x28`). It clamps a level below 1 to 1, then calls `NK.Formula.StatEnhance.CalcCoverStatEnhance(level, CoverStatEnhanceType)` RVA `0x061274E0` for types 0 and 1, passing the returned values into `SpotCharacterCover.Create` RVA `0x06399EE0`. `CalcCoverStatEnhance` looks up `DataManager.CoverStatEnhanceTable` (DataManager offset `+0x248`, metadata type `DataLayerTable<...,CoverStatEnhanceRecord,...>`). The `CoverStatEnhanceRecord` fields are `Id`, `Lv`, `Level_hp`, `Level_defence`. Thus the proven battle cover HP/defence input is the character's constructed **level**, through the original cover table. I found no `CoverStageLv` read in the two original Intercept constructors or in this cover-creation chain. Its value 8 must not be substituted for character level 200/400 or injected as an invented transporter field.

The current `mechanics_fixture.js` calls `SpotCharacterData.set_Level` from each request member and lets the original character constructor make the cover. Current schema-2 validation in `mechanics_request.py` requires Special member levels to equal source `CharacterLv=200`; its Anomaly check rejects levels above `LimitCharacterLv=400`. The new Special fixture therefore **does not have the earlier suspected 400-versus-200 cover-level mismatch**. This proves level-input agreement for valid Special diagnostic requests, not full corrected-snapshot parity. Anomaly requests below 400 need a separate check of the original correction overload's exact level behavior before a claim of account-faithful stats or cover values.
